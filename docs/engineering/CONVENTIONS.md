# 开发与文档规范

状态：已接受

日期：2026-10-25

## 文档分类

### `docs/`

用于记录已核实事实、已接受决策和明确标注为目标的设计。

- Markdown 文件名使用全大写，例如 `WORKSPACE.md`。
- 子目录使用全小写 snake_case。
- 文档开头可记录状态与日期；行为变化时更新原文，而不是堆叠互相矛盾的决定。
- 目标架构、当前实现和后续非目标必须清楚区分。

### `notes/`

用于记录调研、假设、尝试、备选方案、失败原因和阶段性结论。

- 目录与 Markdown 文件名均使用全小写 snake_case。
- 记录使用日期、信息来源和验证范围。
- 未验证的推断必须标为推断，不得写成事实。
- 形成最终方案后更新对应 docs，并在两者之间建立链接。

## 注释原则

注释应当少而有用，优先通过命名、类型和函数边界表达意图。

- `///`：说明公共 API 调用者需要知道的语义、错误、生命周期和副作用。
- `//!`：只为确有整体约束的模块提供模块级说明。
- `NOTE:`：解释非显然约束、不变量或兼容性原因。
- `SEE:`：引用规范、固定版本源码或详细设计；引用不能代替必要的本地解释。
- `FIXME:`：标记已确认的缺陷，说明影响或触发条件；能够立即修复时不留下 FIXME。
- `TODO:`：只记录具体、可执行且确实需要延后的事项。
- `SAFETY:`：如果未来确有必要引入 `unsafe`，必须完整说明安全前置条件及成立理由。

不写显而易见的逐行复述，不用注释保留废弃实现，不批量添加无信息量的文档注释。

## Rust 实现

- 使用 Rust 2024 edition 和 workspace 统一管理的依赖版本。
- 可恢复错误通过结构化错误传播，不以 panic 作为正常控制流。
- 核心 crate 不依赖 GPUI 类型；UI 不直接拼装下载或启动细节。
- 文件写入考虑中断与并发，配置和安装结果不能只凭“文件存在”判定成功。
- 外部命令通过参数数组启动，不经过 shell 拼接。
- 日志、错误和诊断输出默认脱敏，尤其是账号令牌与授权 URL 中的敏感参数。
- 网络、文件系统和平台集成应能在测试中使用固定输入或替身，不要求所有逻辑都做成全局单例。

## 测试与验证

- 纯逻辑优先使用普通 Rust 测试，避免为了测试引入图形环境。
- 版本 JSON、规则、继承、参数生成等采用固定 fixtures 或 golden tests。
- 下载测试覆盖候选源顺序、超时、重试、取消、哈希不符和中断恢复；默认不访问真实服务。
- 集成测试不得需要真实 Minecraft 账号，也不得把令牌写入 CI 日志。
- 三平台编译成功只证明可构建；图形界面、游戏启动和发布包仍需对应平台的运行验证。

常规检查命令：

```bash
cargo fmt --all -- --check
cargo clippy --workspace --all-targets -- -D warnings
cargo test --workspace
```

## Git 提交

每个完整且验证通过的任务都应留下独立提交，采用 Conventional Commits 格式：

```text
<type>(<scope>): <summary>
```

`scope` 可省略。常用类型为 `feat`、`fix`、`docs`、`refactor`、`test`、`build`、`ci`、`perf`、`style`、`chore` 和 `revert`。摘要使用简洁的英文祈使句。

只暂存当前任务相关文件。提交前检查工作区和暂存差异，不夹带用户已有修改、无关文件、令牌或其他秘密。

## 文档改动检查

- 文件名与目录符合上述命名规则。
- 本地 Markdown 链接指向存在的文件。
- 当前状态、目标状态和未决问题没有混写。
- 引用 HMCL 行为时使用 [固定基线](../compatibility/HMCL_BASELINE.md)，并在需要长期保留时链接固定 commit。

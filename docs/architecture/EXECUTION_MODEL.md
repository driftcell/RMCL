# 执行模型

状态：已接受的目标架构

日期：2026-10-25

## 应用级任务

下载、安装、修复、Java 获取和游戏进程都不属于某个临时页面。它们由应用层任务管理器持有，并使用稳定任务 ID 暴露状态。

- UI 切换页面不能隐式取消后台工作。
- 取消必须是协作式的，并区分“已请求取消”和“已经停止”。
- 任务状态至少包含阶段、已完成量、可选总量、当前项目、错误和取消状态。
- UI 与核心之间使用有界事件通道；高频字节进度和日志需要限流或合并，避免无界排队。
- 可恢复错误返回到任务状态和日志，不通过后台 panic 或静默丢弃处理。

GPUI Task 可用于界面状态桥接，但不能成为长生命周期下载或游戏进程的唯一所有者。

## 安装计划

安装前先根据实例、游戏版本、组件、OS 与 CPU 架构生成 `InstallPlan`。计划描述：

- 所需文件及其目标路径
- 候选下载地址、大小与可用哈希
- natives 提取要求
- Java 约束
- 必须执行的安装步骤及依赖顺序

计划生成与副作用执行分离。执行器负责缓存、并发、重试、取消、临时文件、校验和原子提交。

镜像只改变候选来源，不得绕过大小、哈希或格式校验。部分文件写入临时位置，成功验证后才能成为可见的安装结果。重复安装与修复应复用同一套完整性判断。

## 启动计划

启动前生成 `LaunchPlan`，至少描述：

- Java 可执行文件
- JVM 参数与游戏参数
- classpath 与 natives 路径
- 工作目录
- 环境变量及占位符展开结果

启动命令使用参数数组，不通过 shell 字符串拼接。用于诊断的序列化计划必须排除或替换访问令牌等秘密。

进程层独立处理 stdout、stderr、退出码、异常终止与日志导出。界面关闭与游戏进程退出不能默认绑定为一个隐式行为。

## 修复语义

修复是“检查约定范围并补齐或替换不符合预期的文件”，不是无条件删除并重装整个实例。

每一类文件的检查强度必须明确：文件存在、非空、大小、哈希、ZIP/JAR 完整性不能互相替代。HMCL 的具体修复行为可作为参考，但 RMCL 应在自己的文档与测试中声明实际保证，不照搬类名或推断其语义。
